## Что нужно

| Что | Версия | Заметка |
|---|---|---|
| Node.js | 24 | Всё проверялось на 24.18. В `package.json` указано `>=22`, но на других версиях приложение не запускали. |
| npm | 11 | Идёт вместе с Node 24 (проверено на 11.16). |
| PostgreSQL | 15 или новее | Проверено на 17.5. Подойдёт свой сервер или управляемая база у провайдера. |
| Интернет на машине сборки | нужен | `npm ci` качает пакеты, а `next build` один раз скачивает шрифты Golos Text и Unbounded с Google Fonts и дальше отдаёт их с вашего сайта. Если сервер сборки не видит Google, шрифты придётся подключить из файлов (см. [`АДАПТАЦИЯ.md`](АДАПТАЦИЯ.md)). Посетители сайта к Google не обращаются. |

Устанавливайте зависимости командой `npm ci` без `--omit=dev`: скрипты базы (`tsx`) и сборка (Tailwind, TypeScript) лежат в `devDependencies`.

## Локальный запуск

Нужна пустая база PostgreSQL. Если её нет, самый быстрый путь с Docker (пример, пароль замените):

```bash
docker run --name zaprosto-pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=zaprosto -p 5432:5432 -d postgres:17
```

Дальше из папки проекта:

```bash
npm ci
cp .env.example .env.local        # в Windows cmd: copy .env.example .env.local
```

Откройте `.env.local` и заполните:

```
DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5432/zaprosto
APP_ORIGIN=http://localhost:3000
TOKEN_SECRET=<строка из команды ниже>
OWNER_PASSWORD=<ваш пароль, не короче 10 символов>
```

Секрет для `TOKEN_SECRET` (получается строка в 43 символа):

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

Затем:

```bash
npm run db:migrate       # создаёт таблицы
npm run db:seed          # прайс из 69 работ, настройки компании, пароль владельца
npm run dev              # http://localhost:3000
```

- Сайт: <http://localhost:3000>. Кабинет: <http://localhost:3000/admin> (откроется страница входа).
- Если `OWNER_PASSWORD` не задан, а база локальная (адрес `localhost`, `127.0.0.1` или `::1`), посев ставит демо-пароль `ladno-demo-2026`. Это сделано только для разработки. Свой пароль можно задать в любой момент: `npm run owner:password -- "новый пароль"`.
- `npm run db:reset` удаляет **все** данные базы и заново применяет миграции и посев. Скрипт отказывается работать, если адрес базы не локальный. Но проверяется только текст адреса: через SSH-туннель на `127.0.0.1` он «увидит» локальную базу и сотрёт боевую. Туннели к боевой базе для `db:reset` и `db:seed` не используйте.
- Проверки кода: `npm run typecheck`, `npm run lint`, `npm test`. Для `npm test` нужна отдельная пустая база и переменная `TEST_DATABASE_URL`; её имя обязано оканчиваться на `_test`. **Перед каждым прогоном тесты стирают схему в этой базе.** Не указывайте на неё ничего ценного.

## Переменные окружения

Значения задаёт тот, кто разворачивает сайт. Секреты лежат только на сервере, в браузер они не попадают.

| Переменная | Нужна | Когда читается | Что делает |
|---|---|---|---|
| `DATABASE_URL` | да | сборка, запуск, скрипты базы | Строка подключения к PostgreSQL. |
| `APP_ORIGIN` | да | **сборка и запуск** | Адрес сайта без слэша на конце, например `https://master.example.ru`. |
| `TOKEN_SECRET` | да | запуск | Секрет не короче 32 символов, из которого строятся приватные ссылки на заявки. |
| `OWNER_PASSWORD` | при посеве | `db:seed`, `owner:password` | Пароль владельца. В базе хранится только хеш (scrypt). На работающем сервере приложение эту переменную не читает: после посева её можно убрать из окружения. |
| `CLIENT_IP_HEADER` | рекомендуется | запуск | Имя заголовка, в котором прокси присылает IP посетителя. |
| `DB_PREPARE` | по необходимости | запуск | `false` отключает prepared statements (нужно за пулером соединений). |
| `DB_POOL_MAX` | по необходимости | запуск | Размер пула соединений, по умолчанию 5. |
| `TEST_DATABASE_URL` | только для тестов | `npm test` | Отдельная база, имя оканчивается на `_test`. |
| `PORT` | нет | запуск | Порт `next start` (по умолчанию 3000). |

Подробно по каждой.

**`DATABASE_URL`.** Формат `postgres://пользователь:пароль@хост:порт/база`. Если в пароле есть спецсимволы (`@`, `/`, `#`), закодируйте их (`%40`, `%2F`, `%23`). Для боевой базы включите у провайдера TLS и добавьте в адрес `?sslmode=require`, если провайдер этого требует.

**`APP_ORIGIN`.** Схема, домен и порт, как их видит посетитель: `https://master.example.ru`. Используется в двух местах, и поэтому значение должно быть одним и тем же при сборке и при запуске:

- при **сборке** в страницы запекаются адреса для `sitemap.xml`, `robots.txt`, картинки для соцсетей и разметка для поисковиков;
- при **запуске** по нему проверяется заголовок `Origin` у всех изменяющих запросов (отправка заявки, загрузка фото, действия в кабинете). Если не совпал, сервер отвечает 403 `bad_origin`.

Проверено: сайт собран с `APP_ORIGIN=https://master.example.ru`, запущен с `https://other.example.org`. Карта сайта осталась со старым адресом, а запрос с `Origin` старого домена был отклонён. Поэтому при смене домена сайт нужно пересобрать. Пока `APP_ORIGIN` не задан, берётся `http://localhost:3000`.
Сайт должен жить на одном адресе: если домен открывается и с `www`, и без, настройте перенаправление на основной адрес, иначе заявки с «второго» адреса не пройдут проверку.

**`TOKEN_SECRET`.** Не короче 32 символов (без него сайт не сможет создать заявку). Получить:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

Секрет храните в менеджере паролей, в репозиторий не кладите. Что будет, если его сменить, написано [ниже](#смена-token_secret).

**`OWNER_PASSWORD`.** Не короче 10 символов. Скрипты `db:seed` и `owner:password` кладут в базу хеш, сам пароль нигде не сохраняется. На сервере, где посев уже выполнен, переменную можно не держать.

**`CLIENT_IP_HEADER`.** Ограничения частоты (вход в кабинет, заявки, загрузка фото) считаются по IP посетителя. Приложение само не может знать настоящий IP, его сообщает прокси. Правила:

- задан `CLIENT_IP_HEADER`: берётся последнее значение этого заголовка;
- не задан: берётся самое правое значение `X-Forwarded-For`;
- заголовка нет совсем: все посетители считаются одним адресом `local`, и тогда общие лимиты («10 заявок в час» и т. п.) делятся на всех сразу.

За nginx из примера ниже задайте `CLIENT_IP_HEADER=x-real-ip` (nginx перезаписывает этот заголовок значением `$remote_addr`, подделать его с клиента нельзя). На Vercel тоже `x-real-ip`. Если приложение смотрит в интернет без прокси, не полагайтесь на лимиты: клиент сам пришлёт любой заголовок. Не выставляйте порт Node наружу, закройте его фаерволом или слушайте только `127.0.0.1`.

**`DB_PREPARE` и `DB_POOL_MAX`.** Нужны, когда между приложением и базой стоит пулер соединений (PgBouncer, Neon pooler, Supabase pooler) в режиме transaction: он не поддерживает prepared statements.

- Если в адресе базы есть слово `pooler` или `pgbouncer`, prepared statements отключаются сами.
- Пулер с другим именем хоста (например, `10.0.0.5:6432`): задайте `DB_PREPARE=false` вручную.
- `DB_POOL_MAX` для одного сервера с `next start` оставьте 5 (или 10 при высокой нагрузке). На serverless (Vercel) поставьте 1–3: каждый экземпляр функции держит свой пул, и соединения базы закончатся быстро.
- Миграции (`db:migrate`) запускайте по прямому адресу базы, не через пулер.

## Сборка и запуск в production

Последовательность на сервере (переменные уже в окружении, см. ниже):

```bash
npm ci
npm run db:migrate                 # схема базы
npm run db:seed                    # один раз, при первом запуске (нужен OWNER_PASSWORD)
npm run build                      # нужны APP_ORIGIN и доступная база
npm run start -- -H 127.0.0.1 -p 3000
```

Важное про сборку, проверено на копии проекта:

- **`next build` обращается к базе.** При сборке часть страниц предварительно отрисовывается, и они читают настройки. Если `DATABASE_URL` не задан, сборка падает с ошибкой `DATABASE_URL не задан`. Если задан, но база недоступна, падает с `ECONNREFUSED`. Значит, перед `npm run build` база должна быть доступна и миграции применены. Сборка на базе без посева проходит.
- Цены, настройки и список работ в сборку **не запекаются**: страницы читают их из базы при каждом запросе. После правки цены в кабинете или SQL-запросом сайт показывает новое значение сразу, пересобирать не нужно.
- `next start` по умолчанию слушает все сетевые интерфейсы (`0.0.0.0`). За nginx указывайте `-H 127.0.0.1`.
- Страницы `/dev/*` (стенды разработчика) в production отвечают 404.

Где хранить переменные: удобно файл `/etc/zaprosto.env` с правами `600`, принадлежащий пользователю, от которого работает сайт.

```
DATABASE_URL=postgres://zaprosto:ПАРОЛЬ@db-host:5432/zaprosto
APP_ORIGIN=https://master.example.ru
TOKEN_SECRET=...
CLIENT_IP_HEADER=x-real-ip
```

Скрипты (`db:migrate`, `db:seed`, `owner:password`) читают `.env.local`, но то, что уже стоит в окружении оболочки, главнее (проверено). Для разовых команд: `set -a; . /etc/zaprosto.env; set +a; npm run db:migrate`.

Пример службы systemd (`/etc/systemd/system/zaprosto.service`). Это шаблон: на реальном сервере он не прогонялся, пути поправьте под себя (`which npm`):

```ini
[Unit]
Description=Zaprosto
After=network.target

[Service]
User=zaprosto
WorkingDirectory=/srv/zaprosto
EnvironmentFile=/etc/zaprosto.env
ExecStart=/usr/bin/npm run start -- -H 127.0.0.1 -p 3000
Restart=always

[Install]
WantedBy=multi-user.target
```

Пример nginx (тоже шаблон, не прогонялся на живом сервере):

```nginx
server {
    listen 80;
    server_name master.example.ru;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name master.example.ru;
    # сертификат: sudo certbot --nginx -d master.example.ru (Let's Encrypt, бесплатно, продлевается сам)

    client_max_body_size 13m;      # фото до 12 МБ; по умолчанию у nginx 1 МБ, и загрузка фото не пройдёт

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

Зачем каждая строка:

- `client_max_body_size 13m`: приложение принимает фото до 12 МБ, но браузер заранее уменьшает снимок примерно до 2000 пикселей по большей стороне, так что обычно файл заметно меньше.
- `Host` и `X-Forwarded-Host`: действия в кабинете (Server Actions) Next.js сверяет `Origin` браузера с этими заголовками. Без них часть действий отклоняется.
- `X-Real-IP`: см. `CLIENT_IP_HEADER`.
- HTTPS обязателен: cookie входа в кабинет ставится с флагом `Secure` (в production). По обычному HTTP, кроме `localhost`, войти в кабинет не получится.

## Где разместить

Сайт состоит из одного Node-процесса и базы PostgreSQL. Файлов на диске он не хранит: заявки, фото и настройки лежат в базе.

### Вариант А. Российский VPS или облако, `next start` за nginx и управляемый PostgreSQL

**Рекомендуется для боевого запуска.** Причина закон о персональных данных: в заявках лежат имя, телефон и адрес клиента, а ст. 18 ч. 5 закона № 152-ФЗ требует, чтобы персональные данные граждан РФ записывались, хранились и извлекались с помощью баз данных на территории России. Сервер приложения, база и резервные копии должны находиться в России. Это не юридическая консультация: формулировки и остальные обязанности оператора (политика, согласие, уведомление Роскомнадзора) покажите юристу.

Что взять:

- Виртуальный сервер или облачная машина в российском дата-центре (Yandex Cloud, Selectel, Timeweb Cloud и др.) с Ubuntu LTS или Debian.
- PostgreSQL 15+: управляемая база у того же провайдера (у большинства крупных российских облаков такая услуга есть, проверьте у выбранного) либо собственный PostgreSQL на том же сервере.
- Домен и бесплатный сертификат Let's Encrypt через certbot.

Порядок:

1. Установите Node 24, nginx, git, certbot.
2. Создайте пользователя `zaprosto`, склонируйте проект в `/srv/zaprosto`.
3. Создайте базу и пользователя базы, заполните `/etc/zaprosto.env`.
4. `npm ci`, `npm run db:migrate`, `npm run db:seed`, `npm run build` (раздел выше).
5. Подключите службу systemd и nginx из примеров, выпустите сертификат.
6. Пройдите [чек-лист](#чек-лист-перед-запуском).

Если база на том же сервере, у PostgreSQL порт наружу не открывайте.

### Вариант Б. Vercel и облачный Postgres (Neon, Supabase)

Подходит для **демонстрации** или для аудитории не из России. Эти сервисы находятся за рубежом, так что хранить на них заявки российских клиентов не стоит (см. выше). Подробности по условиям тарифа (например, ограничения бесплатного плана на коммерческое использование) уточните у Vercel.

Что учесть:

- **База должна быть доступна во время сборки на Vercel** и уже содержать схему: в проекте Vercel задайте `DATABASE_URL` для окружения сборки, а миграции и посев выполните заранее с вашего компьютера по прямому адресу базы (`db:migrate`, `db:seed`).
- **Пулер.** Для работы приложения используйте адрес пулера (у Neon это хост с `-pooler`, у Supabase `pooler.supabase.com`). Prepared statements отключаются сами по слову `pooler` в адресе; если пулер называется иначе, добавьте `DB_PREPARE=false`. Поставьте `DB_POOL_MAX=1` (максимум 3).
- **Лимит тела запроса 4,5 МБ** у функций Vercel: запрос больше возвращает 413. Приложение к этому готово: браузер заранее уменьшает фото до 2000 пикселей (JPEG с качеством 0,85), так что одно фото обычно укладывается. Но фото с необычно тяжёлым сжатием всё же может не пройти; тогда клиент увидит ошибку загрузки с кнопкой «Повторить».
- **Переменные Vercel:** `DATABASE_URL`, `APP_ORIGIN` (боевой домен; значение задайте до сборки), `TOKEN_SECRET`, `CLIENT_IP_HEADER=x-real-ip`, `DB_POOL_MAX`.
- Vercel собирает сайт при каждом деплое и берёт `APP_ORIGIN` из настроек проекта, так что при смене домена достаточно поменять переменную и сделать новый деплой.

Сравнение:

| | А. Российский VPS + nginx | Б. Vercel + Neon/Supabase |
|---|---|---|
| Данные клиентов в России | да | нет |
| Подходит для боевого запуска в РФ | да | нет |
| Настройка | выше: сервер, nginx, обновления ОС | ниже: деплой из репозитория |
| Лимит фото | задаёт nginx (13 МБ в примере) | 4,5 МБ на запрос |
| Подключение к базе | напрямую | через пулер, `prepare: false` |

## Резервные копии

В базе лежит всё: заявки, история, настройки, прайс, пароль (хеш) и **фото** (они хранятся в таблице `photos` как `bytea`, в формате WebP не больше 1600 пикселей). Поэтому один дамп базы сохраняет и фотографии. Отдельной папки с файлами нет.

Создать копию (формат `custom`, сжатый):

```bash
pg_dump -Fc -f zaprosto-$(date +%F).dump "$DATABASE_URL"
```

Восстановить в пустую базу:

```bash
createdb zaprosto_restore
pg_restore --no-owner -d "postgres://пользователь:пароль@хост:5432/zaprosto_restore" zaprosto-2026-11-19.dump
```

Проверено на PostgreSQL 17.5: дамп восстановился полностью, включая фото, заявки, прайс и владельца. Версия `pg_dump` должна быть не ниже версии сервера.

Рекомендации:

- Делайте копию каждую ночь (cron) и храните 14–30 последних. Хотя бы раз в месяц копию уносите с сервера: в другое хранилище **в России**, потому что в ней те же персональные данные.
- Раз в квартал восстанавливайте копию в пустую базу и проверяйте, что сайт открывается: непроверенная копия копией не считается.
- Автоматическая копия провайдера управляемой базы не отменяет собственную: свой дамп можно скачать и перенести.
- Размер. Фото занимают основную часть базы. По оценке (не измерялась на реальных заявках) одно фото занимает порядка 100–300 КБ, а в заявке их до трёх. Следить за размером: `select pg_size_pretty(pg_total_relation_size('photos'));`.
- Что не попадает в дамп и хранится отдельно: файл переменных окружения (`/etc/zaprosto.env`, особенно `TOKEN_SECRET` и пароль базы). Держите копию в менеджере паролей.

Пример ночного задания cron (поправьте пути, пользователь должен читать `/etc/zaprosto.env`):

```bash
#!/bin/sh
# /usr/local/bin/zaprosto-backup.sh
set -e
. /etc/zaprosto.env
mkdir -p /var/backups/zaprosto
pg_dump -Fc -f /var/backups/zaprosto/zaprosto-$(date +%F).dump "$DATABASE_URL"
find /var/backups/zaprosto -name '*.dump' -mtime +14 -delete
```

```
30 3 * * * /usr/local/bin/zaprosto-backup.sh
```

## Пароль владельца, первый вход, смена TOKEN_SECRET

### Первый вход

1. Откройте `https://ваш-домен/admin`: вас перенаправят на `/admin/login`.
2. Введите пароль, который вы задали через `OWNER_PASSWORD` при посеве или командой `owner:password`.
3. Сеанс держится 14 дней. Вход ограничен: 10 попыток за 15 минут с одного адреса и 50 за 15 минут всего. Если лимит исчерпан, подождите 15 минут.
4. Первым делом заполните «Компанию» (название, город, территория, контакты), проверьте все цены в «Тарифах» (в посеве цены вымышленные) и решите, нужен ли режим игры («Игра»).

### Смена пароля

- **В кабинете.** Раздел «Доступ»: введите текущий пароль и новый (не короче 10 символов). Все остальные сеансы закроются, в этом браузере вы остаётесь.
- **Забыли пароль.** На сервере: `npm run owner:password -- "новый пароль"`. Команда ставит новый пароль и закрывает **все** сеансы, включая ваш. Чтобы пароль не остался в истории оболочки, можно передать его через окружение: `OWNER_PASSWORD="новый пароль" npm run owner:password`.
- **Выйти везде.** Раздел «Доступ», кнопка «Выйти на всех устройствах».

### Смена TOKEN_SECRET

Ссылка клиента на заявку (`/o/<токен>`) создаётся при отправке заявки: токен считается по секрету и случайному ключу запроса, а в базе остаётся только его хеш (sha256). Когда клиент открывает ссылку, сервер сравнивает хеш из адреса с хешем в базе, секрет в этой проверке не участвует.

Что это значит при смене `TOKEN_SECRET` (проверено запуском: заявка создана, секрет заменён, ссылка открыта):

- **Уже выданные ссылки продолжают работать.** Смена секрета их не отзывает и не ломает.
- Единственный побочный эффект: если у клиента заявка уже сохранилась, но ответ до него не дошёл, и он повторяет отправку **уже после смены секрета**, сервер узнает заявку по ключу запроса, но вернёт ссылку, посчитанную по новому секрету. Такая ссылка не откроется (404). Заявка при этом не потеряна и не задвоена, она видна в кабинете. Шанс на это мал и возможен лишь в окне между отправкой и сменой секрета.
- **Менять секрет ради отзыва выданных ссылок бесполезно.** Если чья-то ссылка попала не туда, закрыть её по отдельности нельзя; можно удалить заявку в кабинете или заменить хеш в базе: `update orders set public_token_hash = encode(sha256(convert_to(gen_random_uuid()::text, 'UTF8')), 'hex') where number = 123;` (123 — номер заявки; выражение проверено на PostgreSQL 17). Клиент после этого потеряет доступ к странице заявки.

Меняйте секрет, когда он мог попасть в чужие руки, лучше в тихое время. Достаточно изменить значение в `/etc/zaprosto.env` и перезапустить службу, пересобирать сайт не нужно.

## Service worker: когда поднимать VERSION

Файл `public/sw.js` даёт офлайн-страницу и быстрый показ статики (3D-модели, постеры, значки). Приватные страницы (`/admin`, `/o/…`, `/checkout`) и `/api/*` он не кеширует. В первой строке кода стоит `const VERSION = "v1"`.

Поднимайте номер (`v2`, `v3`…), когда:

- поменяли офлайн-страницу (`src/app/(site)/offline/page.tsx`), её стили или значки из списка `BRAND` в `sw.js`;
- поменяли логику самого `sw.js`;
- сменили название, значки или шрифты, и хотите, чтобы это увидели в офлайне и те, кто уже заходил.

Как это работает: браузер проверяет `sw.js` при каждой загрузке сайта; байты файла изменились, значит, ставится новая версия, старые кеши (`zaprosto-…`) удаляются при активации. Если номер не менять, офлайн-страница у ходивших раньше посетителей остаётся прежней.

Модели, постеры и значки отдаются из кеша сразу и обновляются в фоне: замену файла модели подхватят при следующем заходе, и поднимать `VERSION` ради этого не нужно. Файлы из `/_next/static/` имеют хеш в имени и меняются с каждой сборкой сами.

## Обновление версии

1. Сделайте резервную копию базы.
2. `git pull` (или распакуйте новую версию), `npm ci`.
3. `npm run db:migrate`: применяются только новые файлы из `db/migrations/*.sql`; журнал ведётся в таблице `schema_migrations`. Откатных миграций нет, поэтому копия из шага 1 нужна.
4. `npm run build` с теми же `APP_ORIGIN` и `DATABASE_URL`.
5. Перезапустите службу: `sudo systemctl restart zaprosto`.
6. Если менялась офлайн-страница или значки, поднимите `VERSION` в `public/sw.js` до сборки.

Не запускайте `npm run db:seed -- --overwrite` на боевой базе: он возвращает **демо-цены и демо-настройки** и перезаписывает пароль владельца значением `OWNER_PASSWORD` (если оно задано), то есть затирает правки владельца. Обычный `db:seed` (без `--overwrite`) ничего не затирает и на боевой базе безопасен.

## Если что-то не работает

| Что видите | Причина | Что делать |
|---|---|---|
| Сборка: `DATABASE_URL не задан` или `ECONNREFUSED` | При сборке нужна доступная база | Задайте `DATABASE_URL`, примените миграции, повторите. |
| 403 `bad_origin` при отправке заявки | `APP_ORIGIN` не совпал с адресом, с которого открыт сайт | Исправьте значение, пересоберите, перезапустите. Проверьте перенаправление `www`. |
| В кабинете после ввода верного пароля снова страница входа | Нет HTTPS (cookie `Secure`) | Включите HTTPS. |
| Действие в кабинете не сохраняется, в логе «Invalid Server Actions request» | Прокси не передал `Host`/`X-Forwarded-Host` | Добавьте заголовки, как в примере nginx. |
| Фото не загружается, ответ 413 | У nginx лимит тела 1 МБ по умолчанию (или 4,5 МБ на Vercel) | `client_max_body_size 13m`. |
| «Слишком много запросов» у всех посетителей | Нет заголовка с IP: все считаются одним адресом | Задайте `CLIENT_IP_HEADER` и `proxy_set_header X-Real-IP`. |
| Ошибки `prepared statement ... does not exist` | Пулер в режиме transaction | `DB_PREPARE=false`. |
| Кабинет: «Слишком много попыток входа» | Исчерпан лимит входа (общий лимит на 50 попыток могли выбрать и посторонние) | Подождать 15 минут. |
